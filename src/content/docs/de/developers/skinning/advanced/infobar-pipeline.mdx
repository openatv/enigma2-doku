A converter is selected for the property its consumer needs. A `Label` reads text. A `Progress` renderer reads `value` and `range`. A visibility converter reads a boolean. Choosing a converter because its name sounds relevant is not enough: its output must match the next stage.

## Three views of the current event

```text
session.Event_Now ── EventInfo(Name) ───────────────────── Label
                 ├─ EventInfo(Duration) ─ ClockToText ───── Label
                 └─ EventInfo(Progress) ────────────────── Progress
```

`EventInfo(Name)` returns the event title as `text`. `EventInfo(Duration)` provides the event duration through `time`, which `ClockToText(AsLength)` turns into minutes and seconds. `EventInfo(Progress)` provides a numeric value with a range of 1000; `Progress` scales that value into the available widget width.

```xml
<widget source="session.Event_Now" render="Label"
        position="40,90" size="1000,44" font="Regular;28"
        foregroundColor="#00FFFFFF" transparent="1">
  <convert type="EventInfo">Name</convert>
</widget>
<widget source="session.Event_Now" render="Label"
        position="1060,90" size="180,44" font="Regular;24"
        foregroundColor="#00FFFFFF" transparent="1">
  <convert type="EventInfo">Duration</convert>
  <convert type="ClockToText">AsLength</convert>
</widget>
<widget source="session.Event_Now" render="Progress"
        position="40,150" size="1200,12"
        foregroundColor="#005BD4EC" backgroundColor="#00344760"
        borderWidth="0">
  <convert type="EventInfo">Progress</convert>
</widget>
```

These are fragments for an existing screen with adequate size. The converter order follows the XML from source toward renderer. `ClockToText` cannot replace `EventInfo(Duration)` because an event source does not itself expose the required duration as clock input.

## Why a widget updates

Sources announce changes to connected elements. Converters receive those changes, invalidate cached derived values as appropriate, and notify downstream renderers. Some converters also poll: event progress and remaining time need to advance between EPG updates. The `@cached` properties avoid repeatedly computing the same value within an update cycle; they are not permanent storage.

Do not add a fast polling timer to every label. Prefer the existing event notifications and a converter's existing polling policy. If a custom source changes a value, call its change notification mechanism; changing an ordinary Python attribute alone does not tell the rendered UI to repaint.

## Missing data is a normal state

No EPG event means there is no meaningful event title, duration or progress. A progress bar showing zero is not evidence that a programme has just started. During zapping, playback changes and empty EPG periods, the UI must tolerate absent data. Test these states separately from a filled example screen.

For a next-event title, a straightforward chain is `session.Event_Next` → `EventInfo(Name)` → `Label`. Avoid adding a second “next-event lookup” converter to a source that already represents the next event unless that converter's documented contract specifically requires it.
